## 들어가며

지금 Next.js의 안정 최신 버전은 **16.3**(2026-08-03 발표, npm `latest`는 16.3.4)이다. 프로젝트를 오래 유지보수하다 보면 "이 옵션이 언제부터 됐더라", "이거 지금도 쓸 수 있는 API인가" 하는 질문이 계속 생기는데, 매번 릴리스 노트를 뒤지는 대신 한 번 정리해두면 편할 것 같아서 14버전부터 16.3까지 훑었다.

App Router는 13(2022-10-25)에서 beta로 처음 등장했다. `app/` 디렉토리, Server Components, 확장된 `fetch`가 이때 나왔고 13.4(2023-05)에서 정식이 됐다. 이 노트는 그 이후, App Router가 실사용 단계로 자리를 잡아가는 과정인 14부터를 다룬다.

범위는 nextjs.org 공식 블로그의 릴리스 포스트와 npm registry 기준이다. 각 메이저 버전마다 브레이킹 체인지와 새로 생긴 기능을 나눠서 적었고, 세부 사용법까지 파고드는 대신 "이 버전에서 뭐가 바뀌었는가"에 집중했다. `cacheComponents`의 구체적인 사용법은 이미 [Next.js 16 cacheComponents](/notes/nextjs-cache-components) 노트에서 다뤘으니 여기서는 16에서 무엇이 달라졌는지만 짚는다.

## Next.js 14 (2023-10-26) — Server Actions 정식화와 PPR 프리뷰

- **Server Actions 정식(Stable)**: `'use server'`를 선언하면 API Route 없이 컴포넌트에서 서버 함수를 직접 호출할 수 있다. form action으로 점진적 향상도 가능하고, `revalidatePath` / `revalidateTag` / `redirect` / `cookies` / `useOptimistic` / `useFormState` / `useFormStatus`와 통합됐다. 데이터 변경과 리렌더, 리다이렉트를 한 번의 네트워크 왕복으로 처리할 수 있게 된 게 핵심이다

```tsx
//* app/actions.ts
'use server'

export async function createPost(formData: FormData) {
  await db.post.create({ title: formData.get('title') })
  revalidatePath('/posts')
}
```

- **Partial Prerendering (프리뷰)**: Suspense 경계를 기준으로 정적 셸을 만들고, 동적 부분은 같은 HTTP 요청 안에서 스트리밍한다. 기존 API를 새로 배울 필요가 없다는 게 특징이었다
- Metadata가 blocking/non-blocking으로 분리됐다. `viewport` / `colorScheme` / `themeColor`가 `metadata`에서 deprecate되고 `viewport` 설정과 `generateViewport`가 새로 생겼다

**브레이킹**
- 최소 Node.js가 18.17로 올라갔다
- `@next/font` 지원이 종료되고 `next/font`로 완전히 넘어갔다
- `ImageResponse`의 import 경로가 `next/server`에서 `next/og`로 바뀌었다
- **`next export` 명령이 제거**되고 `output: 'export'` 설정으로 대체됐다

## Next.js 15 (2024-10-21) — 비동기 요청 API와 캐싱 기본값 전환

App Router를 쓰던 프로젝트라면 실제로 코드를 고쳐야 했던 버전이다.

- **Async Request APIs (브레이킹)**: `cookies`, `headers`, `draftMode`, `params`, `searchParams`가 전부 비동기로 바뀌었다. 요청이 오기 전에 최대한 미리 렌더링하기 위한 사전 작업이었다. 코드모드로 자동 변환할 수 있다

```tsx
//* Next.js 14 이전
export default function Page({ params }: { params: { id: string } }) {
  return <div>{params.id}</div>
}

//* Next.js 15 이후
export default async function Page({
  params,
}: {
  params: Promise<{ id: string }>
}) {
  const { id } = await params
  return <div>{id}</div>
}
```

```bash
npx @next/codemod@canary next-async-request-api .
```

- **캐싱 기본값 변경 (브레이킹)**: `fetch` 요청, `GET` Route Handler, 클라이언트 라우터 캐시가 기본으로 캐시하지 않게 바뀌었다. Page 세그먼트의 `staleTime`이 0이 됐다(레이아웃 데이터, 뒤로가기 복원, `loading.js`의 5분 캐시는 유지). `experimental.staleTimes`로 예전 동작으로 되돌릴 수 있다
- **React 19 지원**: App Router는 React 19 RC를 쓰고 Pages Router는 React 18 하위 호환을 유지했다. React Compiler 실험적 지원도 이때 시작됐다
- **Turbopack Dev 정식(Stable)**: `next dev --turbo`가 정식이 됐다
- `next/form`: prefetch와 클라이언트 내비게이션, 점진적 향상이 되는 `<Form>` 컴포넌트가 추가됐다
- `next.config.ts` TypeScript 지원

**기타 브레이킹 (선별)**
- 최소 Node.js가 18.18.0으로 올라갔다
- `next/image`에서 `squoosh`가 제거되고 `sharp`가 optional dependency가 됐다
- `force-dynamic`을 쓰면 fetch 캐시에 `no-store`가 기본값으로 설정된다
- 렌더 중에 `revalidateTag` / `revalidatePath`를 호출하면 에러가 나게 됐다
- `next/dynamic`의 `suspense` prop이 제거되고, Server Component에서 `ssr: false`를 쓸 수 없게 됐다

## Next.js 16 (2025-10-21) — Cache Components와 Turbopack 기본화

이 버전부터는 캐싱 모델과 번들러가 동시에 바뀌면서 브레이킹 체인지 밀도가 특히 높다.

- **Cache Components**: `next.config.ts`의 `cacheComponents: true` 하나로 `"use cache"` 디렉티브 중심의 완전 opt-in 캐싱이 활성화된다. 모든 동적 코드는 기본적으로 요청 시 실행되고, 컴파일러가 캐시 키를 자동 생성한다. 2023년 도입된 PPR의 완성형인 셈인데, 세부 사용법은 [cacheComponents 노트](/notes/nextjs-cache-components)에서 다뤘다
- **Turbopack 정식 + 기본 번들러**: 프로덕션 빌드가 2배에서 5배 사이로, Fast Refresh는 최대 10배 빨라졌다. webpack을 계속 쓰려면 `next dev --webpack` / `next build --webpack`로 opt-out해야 한다
- **`proxy.ts`가 `middleware.ts`를 대체**한다. 파일명과 export 함수명만 `proxy`로 바꾸면 로직은 그대로고, Node.js 런타임에서 실행된다. `middleware.ts`는 Edge 런타임용으로 남아 있지만 deprecated다

```ts
//* proxy.ts (기존 middleware.ts)
import { NextResponse } from 'next/server'
import type { NextRequest } from 'next/server'

export function proxy(request: NextRequest) {
  return NextResponse.next()
}
```

- **캐싱 API 개선**: `revalidateTag(tag, profile)`이 두 번째 인자로 `cacheLife` 프로파일(`'max'`, `'hours'`, `'days'` 또는 `{ expire: 3600 }`)을 필수로 요구하게 됐다(SWR 동작). 단일 인자 형태는 deprecated다. Server Actions 전용으로 `updateTag(tag)`가 추가돼서 같은 요청 안에서 즉시 최신 데이터를 읽는 read-your-writes가 가능해졌고, `refresh()`는 캐시는 건드리지 않고 캐시되지 않은 데이터만 갱신한다

```ts
//* Server Action 안에서
import { revalidateTag, updateTag } from 'next/cache'

async function publishPost(id: string) {
  'use server'
  await db.post.publish(id)
  updateTag(`post-${id}`) // 이 요청 안에서 바로 최신 데이터 반영
}
```

**버전 요구사항 (브레이킹)**
- Node.js 20.9+ (Node 18 지원 종료), TypeScript 5.1+
- 브라우저: Chrome/Edge/Firefox 111+, Safari 16.4+

**제거 (브레이킹)**
- AMP 지원이 전면 제거됐다(`useAmp`, `config = { amp: true }`)
- **`next lint` 명령이 제거**됐다. Biome나 ESLint를 직접 써야 하고, `next build`가 더 이상 lint를 돌리지 않는다
- `serverRuntimeConfig`, `publicRuntimeConfig`가 제거되고 환경변수로 대체됐다
- **동기 `params` / `searchParams`, `cookies()` / `headers()` / `draftMode()` 접근이 완전히 제거**됐다. 15에서는 경고였던 것이 16에서는 에러가 된다. 반드시 `await`해야 한다

**동작 변경**
- `images.minimumCacheTTL`이 60초에서 4시간(14400초)으로 늘었다
- `images.qualities`가 `[1..100]`에서 `[75]`로 좁혀졌다(quality prop은 가장 가까운 값으로 강제된다)
- **모든 병렬 라우트 슬롯에 `default.js`가 필수**가 됐다. 없으면 빌드가 실패한다(`notFound()` 호출이나 `null` 반환으로 기존 동작을 재현해야 한다)
- `next dev`와 `next build`가 별도 출력 디렉토리를 쓰게 돼서 동시 실행이 가능해졌다

## Next.js 16.1 / 16.2 / 16.3 (2025년-2026년)

마이너 버전이지만 실사용에 체감되는 변화가 많아서 따로 묶었다.

### 16.1 (2025-12-18)

- Turbopack **파일시스템 캐싱**이 `next dev`에서 정식 + 기본 활성화됐다. 첫 라우트 컴파일이 react.dev 기준 3.7초에서 380ms(약 10배), nextjs.org 기준 3.5초에서 700ms(약 5배)로 줄었다
- Next.js Bundle Analyzer(실험적): `next experimental-analyze`
- `next dev --inspect`로 Node.js 디버거를 연결할 수 있게 됐다(기존 `NODE_OPTIONS=--inspect`는 모든 하위 프로세스에 붙는 문제가 있었다)
- `next upgrade` 명령이 신설됐다

### 16.2 (2026-03-18)

- 개발 서버 Time-to-URL이 16.1 대비 약 87% 단축됐다
- **렌더링이 약 50% 빨라졌다**. React에 기여한 변경으로 RSC 페이로드 역직렬화가 최대 350% 빨라졌는데, `JSON.parse`의 reviver 콜백이 키-값마다 C++/JS 경계를 넘던 방식을 순수 JS 재귀 walk로 대체한 결과다. 실제 앱 기준 HTML 렌더가 25%에서 60% 사이로 개선됐다
- 기본 에러 페이지가 리디자인됐고, 개발 터미널에 Server Function 로깅(함수명, 인자, 실행 시간, 정의 파일)이 추가됐다
- `next/link`에 `transitionTypes` prop이 생겨서 `React.addTransitionType`에 전달할 수 있게 됐다(App Router 전용)
- **Adapters 정식(Stable)**

### 16.3 (2026-08-03) — 현재 최신

이번 버전은 코드 변경 없이 모든 앱에 적용되는 개선이 특히 눈에 띈다.

- **개발 메모리 최대 90% 감소**: dev 디스크 캐싱과 메모리 eviction이 기본 활성화됐다. vercel.com 대시보드 기준 21.5GB에서 2GB로 약 90% 줄었고, nextjs.org 기준 4,600MB에서 840MB로 약 82% 줄었다
- **빌드 캐싱**: `next build`에도 디스크 캐싱이 기본 적용됐다. nextjs.org는 21초에서 9.2초로(약 2.3배), vercel.com/geist는 30초에서 5.5초로(약 5.5배) 단축됐다
- **TypeScript 7 지원**: `next build`의 타입 체크에 TypeScript 7(네이티브 포트, 10배 빠름)을 쓸 수 있다
- **SSR이 22% 더 많은 요청을 처리**한다. App Router 렌더 레이어를 web streams에서 네이티브 Node.js 스트림으로 교체해서 변환 오버헤드를 없앤 결과다
- **커스텀 에러 바운더리 정식**: `next/error`의 `catchError`. `notFound` / `redirect`를 방해하지 않고, `retry()`로 실패한 Server Component를 서버에서 재요청할 수 있다
- **Root params**: `next/root-params`에서 `import { lang } from 'next/root-params'` 형태로, root layout 위쪽에 정의된 동적 세그먼트를 prop drilling 없이 어느 Server Component에서든 `await lang()`으로 접근할 수 있다. 현재는 Server Component 전용이다

```ts
//* app/[lang]/page.tsx가 아니라 더 깊은 곳의 Server Component에서
import { lang } from 'next/root-params'

async function Greeting() {
  const currentLang = await lang()
  return <p>{currentLang}</p>
}
```

- **Instant Navigations (opt-in)**: `cacheComponents: true`와 `partialPrefetching: true`를 함께 켜면 활성화된다. Server Components가 JS를 줄이고 워터폴을 없앤 대신 내비게이션이 느리게 느껴지고, 암묵적 캐싱 모델이 동적 앱에는 맞지 않던 문제를 `'use cache'` 프리미티브를 클라이언트 캐싱까지 확장해서 해결하려는 방향이다. 이 동작들은 향후 메이저 버전에서 기본값이 될 예정이라고 밝혔다

## 정리

### 메이저 버전 한눈에 보기

| 버전 | 날짜 | 핵심 변화 |
|------|------|-----------|
| 14 | 2023-10-26 | Server Actions 정식, PPR 프리뷰 |
| 15 | 2024-10-21 | 비동기 요청 API, 캐싱 기본값 반전 |
| 16 | 2025-10-21 | Cache Components, Turbopack 기본 번들러, `proxy.ts` |

### 최소 Node.js 버전 변화

| Next.js 버전 | 최소 Node.js |
|--------------|--------------|
| 14 | 18.17 |
| 15 | 18.18.0 |
| 16 | 20.9+ |

### 업그레이드 시 주의할 점

버전 사이 간격이 벌어질수록 손이 많이 가는 지점이 정해져 있다.

- **15로 넘어갈 때**: `params` / `searchParams` / `cookies` / `headers`를 동기로 쓰던 코드가 전부 걸린다. 코드모드(`next-async-request-api`)를 돌려도 타입 단언이 필요한 애매한 케이스는 수동으로 봐야 한다
- **16으로 넘어갈 때**: 15에서 경고만 뜨던 동기 접근이 이제 에러가 되므로, 15에서 경고를 무시하고 넘어온 프로젝트라면 16에서 한꺼번에 터진다. 병렬 라우트를 쓰고 있다면 `default.js` 누락 여부도 미리 확인해야 빌드가 안 깨진다
- `next lint`를 쓰던 CI 파이프라인이 있다면 16에서 명령 자체가 사라지므로 ESLint CLI나 Biome로 미리 전환해야 한다
